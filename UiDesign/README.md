# Handoff: IBERO Cálculo 3 — UI/UX Redesign

## Overview
A UI/UX redesign for the "Plataforma Cálculo 3" LMS-style app (repo: `SernaEd/FirmsSimulationClass`, branch `main`, Next.js 14 App Router + Tailwind frontend, FastAPI backend). The redesign covers the welcome/auth screen, the student dashboard ("Inicio"), and the team screen ("Mi equipo"), plus a written UX audit of the rest of the app. The goal: move the product's currently plain/bordered-box UI toward a dark, IBERO-branded interface with real visual hierarchy and lightweight gamification motion (token count-up, streak calendar, hover micro-interactions), since the platform's core purpose is a token/privilege economy students should *want* to open daily.

## About the Design Files
The `prototype/` folder is a **design reference built in HTML** (an internal "Design Component" format, self-contained and viewable directly in a browser — open `prototype/IBERO Cálculo 3 - Rediseño.dc.html`). It is a clickable, non-functional mockup: navigation between the three screens works, buttons don't call any real API. **Do not copy this HTML into the Next.js app.** The task is to recreate this design's layout, spacing, color, type, and interactions as real React components inside the existing `frontend/` Next.js + Tailwind + TypeScript codebase, wired to its real data (`lib/api.ts`, `useAuth`, etc.), following the app's existing component conventions (see `frontend/components/`, e.g. `BalanceWidget`).

## Fidelity
**High-fidelity.** Colors, spacing, type scale and component states below are final — implement pixel-close using Tailwind utilities/theme extension, not placeholders.

## Design system this build is grounded in
The mockups use the **Nocturne** design system (bundled in `prototype/_ds/nocturne-.../`) as the base token set and component vocabulary, with one deliberate override: Nocturne's default blurple accent is replaced with an IBERO red, and the blurple ramp is kept as a secondary accent (used for the "Modelador" role tag and similar secondary indicators). Read `prototype/_ds/nocturne-172cc265-6033-42f0-8772-f22fcece377d/readme.md` for the full system rationale (spacing scale, elevation, "why outlined buttons," etc.) — the app's Tailwind config should encode these same tokens (see Design Tokens below) so future screens stay consistent without re-deriving them.

## Screens

### 1. Bienvenida (Welcome / auth)
- **Purpose**: Landing + register/login entry point (maps to `frontend/app/page.tsx`, `login/`, `registro/`).
- **Layout**: Centered column, max-width 1080px, top padding 88px. Two-part vertical stack:
  1. Hero row: `grid-template-columns: 1fr 0.85fr`, gap 22.4px (`--space-8`), vertically centered. Left: kicker + H1 + subhead. Right: an inline SVG illustration (4:5 aspect ratio, `border-radius: 14px` / `--radius-lg`, `box-shadow: var(--shadow-lg)`) — see Implementation notes below for why this replaced the mock's photo.
  2. Below (56px+ gap): a small uppercase label ("Empieza en menos de un minuto"), then a 2-column card grid (gap 56px) — "Crear cuenta" and "Iniciar sesión" cards.
- **Hero copy** (verbatim):
  - Kicker: "Ecuaciones Diferenciales" — no "IBERO ·" prefix, see Implementation notes below.
  - H1: "Tu firma consultora empieza aquí." — 56px, line-height 1.05, max-width ~13ch, weight 500 (Inter — never bolder)
  - Subhead: "Resuelve casos reales de modelado matemático en equipo, gana Tokens por tu trabajo y canjéalos por privilegios académicos." — 18px, color `--color-neutral-400`, max-width ~46ch
- **Cards**: each `padding: 40px 16.8px` (`--space-6` horizontal), an outline icon (36px, stroke `--color-accent-300` for the register card / `--color-neutral-300` for login), a title (17px, card-title style), a body line (13px, 70% opacity), and one button (`.btn-primary` for register — outlined red; `.btn-secondary` for login — outlined neutral).
- **Card hover**: `transform: translateY(-6px)`, `box-shadow: var(--shadow-lg)`, border fades in (`--color-accent-700` on the register card, `--color-neutral-700` on login), transition `.25s ease` on transform/shadow/border-color. Cursor pointer on the whole card, not just the button.
- **Fade-in on load**: each hero/card block animates in with a `fadeUp` keyframe (opacity 0→1, translateY 10px→0, `.5s ease`), staggered ~50ms apart (kicker → H1 → subhead → hero image → cards).
- Footer line: "Antes de registrarte, consulta las reglas y el aviso de privacidad." — 13px, `--color-neutral-500`.

### 2. Dashboard ("Inicio")
- **Purpose**: Student home — replaces the current plain link-list `frontend/app/inicio/page.tsx`.
- **Layout**: max-width 880px, padding `22.4px 11.2px 80px` (`--space-8 --space-4`).
  - Header: kicker "Cálculo 3" (no "IBERO ·" prefix — see Implementation notes below), H1 "Hola, {nombre}" (30px), a meta line showing firm name + active module.
  - Row 1 (grid `1.1fr .9fr`, gap 11.2px): **Racha (streak) card** and **Saldo del banco (token balance) card**.
  - Row 2: "Accesos rápidos" — a 4-column card grid of quick-access tiles (icon + label), one tile flagged "Nuevo" for the not-yet-built file upload/preview feature.
- **Streak card**: kicker "Racha activa", a big number (38px, tabular) + "días seguidos" label, a flame icon (outline, `--color-accent-400`) top-right. Below: an 8-cell grid (2 weeks × Mon–Thu, the only days that count per the app's streak rules) — each cell 40px tall, rounded (`--radius-sm`), showing a weekday-letter + either a checkmark (done, tinted `--color-accent-800` bg / `--color-accent-300` text), a shield icon (streak-freeze used, tinted with the *secondary* accent ramp `--color-accent-2-800`/`-300`), an outlined "today" state (`--color-accent-400` border, no fill), or a plain neutral cell (future/not-yet-reached). Cells pop in on mount (`popIn` keyframe: scale .6→1, opacity 0→1, staggered 60ms apart, `cubic-bezier(.2,1.4,.4,1)` for a slight overshoot). Below the grid: "Siguiente hito: N días" / "+30 Tks" row, then a 6px rounded progress bar (`--color-neutral-800` track, gradient fill `--color-accent-600`→`--color-accent-400`, animates width on change over 1s).

Below: last 3 ledger movements (source name left, `+N Tks` right in `--color-accent-300`), each row separated by a 1px `--color-neutral-900` bottom border. Footer: a ghost button "Ver movimientos" linking to the full paginated ledger (existing `/movimientos` page).
- **Quick-access tiles**: 4-column grid, gap 8.4px (`--space-3`), each a card (elev-sm) with an outline icon (20px, `--color-accent-400`) + 13px label, `cursor:pointer`, hover: lift 2px + border tint `--color-accent-600`. Tiles: Mi equipo, Privilegios, Foro, **Entregas y archivos** (new — tag "Nuevo" top-right in an outlined tag).

## Interactions & Behavior
- **Screen nav**: top nav bar (`.nav` component) persists across all three screens — brand mark left, "Inicio"/"Mi equipo" real nav links, right-aligned segmented control (Bienvenida / Auditoría UX) in the prototype only — in the real app this becomes normal top-level routing, no segmented control needed.
- **Token count-up**: on entering the dashboard, animate the balance number from 0 to its real value, ease-out-cubic, ~1s. Re-run this only on a real balance *change* (not on every re-render) in production — e.g. animate from old value to new value when a purchase/kudos changes the balance.
- **Card hover states**: every clickable card lifts (`translateY(-2px)` to `-6px` depending on size) and gains a colored border on hover — never just a background darken, which is too subtle to read as "clickable" against Nocturne's already-dark surfaces.
- **Streak cell entrance**: stagger-animate in on first paint of the dashboard (not on every re-render — guard with a "seen" flag/localStorage or component-mount-only state).
- **Focus states**: rely on Nocturne's existing `:focus-visible { outline: 2px solid var(--color-accent) }` — don't override.

## State Management
- Dashboard needs: `user` (name, pronouns, active module), `tokenBalance` (number, drives the count-up), `movements` (last 3 ledger entries), `streakDays` + `streakCells` (last 8 school-day states: done/shield/today/future), `nextMilestone` + `progressPct`.
- Team screen needs: `team` (name, member list with id/name/role/avatar-initials), `chatMessages` (paginated/live via the existing team WebSocket chat, not built in this mock), `teamStats` (Tokens total, last licitación placement).
- Both screens are currently static/mocked in the prototype — wire to real endpoints (`GET /me/tokens`, `GET /me/tokens/movements`, `GET /me/team`, team chat websocket) per `implementation_plan_v2.md`.

Font: Inter for heading and body (`--font-heading` / `--font-body`), weight 500 max for headings (never bolder — hierarchy is via size/space, not weight). Spacing/radius/shadow: use Nocturne's `--space-*` / `--radius-*` / `--shadow-*` scale as-is, do not invent new values.

**Contrast note**: don't use `--color-accent` (500, fully saturated) directly as *text* on the dark surfaces — it fails readability. Always use `--color-accent-300` for accent-colored text/labels/icons at body sizes, and reserve full-saturation `--color-accent` for borders, large icons, and background tints.

## Implementation notes (deviations from the mock)

First implementation pass (app-wide redesign, 2026-08-19) found real gaps between this mock and the running app. Each is a deliberate, documented decision — not a shortcut — so the next person doesn't "fix" it back to the literal mock:

- **Streak card shipped as a placeholder in this pass** (`/me/streak` didn't exist yet) — since superseded by a real implementation; see "New feature: Motor de Racha Diaria" below for the current shape and how it deviates from the spec'd 8-day grid.
- **Team chat and team "Resumen" card ship as placeholders**, for the same reason: no chat backend/websocket, and no endpoint for team Tks-total / licitación placement. `frontend/app/mi-equipo/page.tsx` renders both card shells with a "Próximamente" state.
- **Dashboard quick-access grid uses the app's real routes**, not the mock's: Mi equipo, Privilegios, Mis tickets, Movimientos, Décimas, Sesión 1 — 6 tiles instead of the mock's 4 (Foro and "Entregas y archivos" aren't built). Grid is `grid-cols-2 sm:grid-cols-3 md:grid-cols-4` to accommodate the extra tiles.
- **Admin links were dropped from the student dashboard entirely**, rather than re-skinned in place — this directly implements the prototype's own UX-audit finding #4 ("stop burying Admin inside the student dashboard"; `TopNav.tsx`'s existing Admin dropdown group is the "distinct switch to admin" affordance the audit asks for), so keeping them in `inicio/page.tsx` too would have reintroduced the exact pattern the audit flags.
- **Nav stays the existing accessible hamburger/dropdown** (`TopNav.tsx`), not the mock's 2-link inline bar — the real app has ~7 student routes plus an admin group, which won't fit inline. Only colors/spacing were reskinned; `aria-expanded`/focus handling is untouched.
- **Tailwind implementation mapping**: tokens are expressed as Tailwind `theme.extend` colors (`accent-*`, `accent2-*`, a custom `neutral-*` ramp, `surface.*`, `radius-*`, `shadow-*`) in `frontend/tailwind.config.ts`, not the prototype's plain-CSS component classes — matching this codebase's existing convention of inline Tailwind utility classes rather than introducing a parallel CSS layer. `ibero.red`/`ibero.red-dark` are kept as Tailwind aliases onto `accent-500`/`accent-700` (identical computed color) so the ~50 pre-existing `bg-ibero-red` call sites didn't need a mechanical rename; new/touched markup uses `accent-*` directly.
- **No solid accent fills, anywhere** — Nocturne's own rule (`.btn-primary` is an outline, never a fill) was applied literally: every pre-existing solid `bg-ibero-red`/`bg-white` action button app-wide was converted to the outlined `border-accent-500 text-accent-300 hover:bg-accent-500/10` treatment, not just the 3 flagship screens.
- **Pages beyond the 3 flagship screens** (login, registro, movimientos, privilegios, mis-tickets, decimas, reglas, test-perfil, clase1, admin/economia, admin/equipos, admin/sistema) got the token upgrade + button-hierarchy/tag-color fixes described above, but no bespoke pixel layout — this doc doesn't spec them, so a systematic pattern pass (not a redesign) was applied to avoid improvising un-reviewed new layouts for the admin/data-heavy screens.
- **`admin/contenido`, `/clases`, `/clases/[id]`** (added 2026-08-19, replacing the never-built Notion-sync plan — the professor edits sessions directly instead) follow the same systematic pattern: existing card/form/inline-edit conventions from `admin/economia` (`CatalogRow`-style create/edit/delete cards) and `admin/equipos` (`toggleSet`-driven expand/collapse), no new layout invented. The session detail page (`/clases/[id]`) ships a static "Comentarios — próximamente" placeholder card until "Comentarios por Clase" (Iteración 1) is built — styled as a dashed-border `border-dashed border-surface-border` empty-state card (matching the "+ Nuevo X" create-form affordance's border treatment elsewhere in these pages), **not** the dashboard's pill-badge "Próximamente" treatment (`StreakCard`/team-chat) — two different placeholder idioms now coexist; pick one deliberately before adding a third. `/clase1` and its hardcoded nav/dashboard links were originally untouched and left running in parallel — `/clases` was additive, not a replacement, per the professor's explicit call. **Superseded 2026-08-25** — see "Third implementation pass" below: `/clase1` was consolidated into `/clases` once the duplication (two different nav paths to what read as the same "Sesión 1") caused real confusion.
- **Feature-flag gating (`decimas_enabled`, added 2026-08-20)**: `/decimas` conditionally hides its "Solicitar Décimas" form behind a `useFeatureFlag` check, replacing it with the same dashed-border empty-state card described above when the flag is off (history stays visible either way). The nav entry (`TopNav`) and dashboard tile (`/inicio`) are hidden outright rather than shown-disabled. This is the first flag-gated screen; reuse this exact pattern (dashed-border notice + hide nav/tile) for future flag-gated features instead of improvising a new one.
- **"IBERO" dropped from every screen kicker and the site `<meta description>`**: `TopNav`'s logo already carries the IBERO brand on every screen, so repeating it in kickers and page metadata was redundant. Welcome-screen kicker and `<meta description>` (2026-08-19): now reads just "Ecuaciones Diferenciales" (`frontend/app/page.tsx`, `frontend/app/layout.tsx`). Dashboard kicker (2026-08-24): now reads just "Cálculo 3" (`frontend/app/inicio/page.tsx`, was "IBERO · Cálculo 3"). `frontend/app/test-perfil/page.tsx`'s kicker was already just "Cálculo 3" and needed no change.
- **Hero photo replaced with an inline differential-equation SVG (2026-08-19)**: no real photo of students/team was ever shot, so the mock's `image-slot` placeholder was replaced with a custom inline SVG (`frontend/app/page.tsx`) — a slope field with sample solution curves, axes, and the label `dy/dx = f(x, y)`, on the same dark gradient/graph-paper background the mock specified. This is more on-brand for a differential-equations course than a generic team photo and needs no photo asset. If a real team photo is shot later, swap it back in per the original spec (4:5 photo, `.lighten` blend) — the SVG is a placeholder-with-more-effort, not a final design decision.

## Second implementation pass: space + motivating actions (2026-08-24)

A follow-up pass across the shipped app (not a new mock — this section is now the source of truth for these patterns going forward, alongside the token table above):

- **"Accesos rápidos" removed from the dashboard entirely** (`frontend/app/inicio/page.tsx`) — every route it linked to (Mi equipo, Privilegios, Mis tickets, Movimientos, Décimas, Sesión 1, Clases) is already reachable from `TopNav`'s menu, so the grid was pure duplication once the nav existed. This supersedes the "Dashboard quick-access grid uses the app's real routes" note above — there is no quick-access grid anymore. `QuickTile` and its per-tile inline icons were deleted from `inicio/page.tsx` rather than left unused.
- **Motivating action banner** — a new shared component, `frontend/components/ActionBanner.tsx`: a full-width card (icon in an accent-tinted circle, title + one-line description, an outlined button on the right) that points at the one action a screen most wants the person to take next. Same hover language as the Bienvenida hero cards (`-translate-y-0.5` lift + accent border tint on hover), `shadow-md` elevation. Used on: `/inicio` (→ Privilegios, replaces the old quick-access grid's vertical space), `/movimientos` (→ Privilegios — a passive history screen gets a reason to act). (`/clases` originally had one pointing at `/clase1` too — removed 2026-08-25 once Sesión 1 became a real entry in the modules grid it sits above; see "Third implementation pass" below.) Reuse this component for any new screen that needs a "next step" nudge rather than hand-rolling another icon+text+button row — that duplication is exactly what this component replaced.
- **Screens without a natural new CTA got a smaller, in-place one instead of a forced banner**: `/mi-equipo`'s "nombre de la firma aprobado" state now links to Privilegios inline (the team-formation task is done; spending Tokens is the next one); `/mis-tickets` got a persistent header-level "+ Comprar privilegio" button instead of only showing that link on the empty state; `/test-perfil` got an answered/total progress bar (reusing the existing accent gradient from the dashboard's streak progress bar) so finishing the test reads as a countable, motivating task instead of an open-ended form.
- **Card style converged on the actual Nocturne convention.** Per `UiDesign/prototype/_ds/nocturne-.../readme.md` ("Components" and "Do"), cards are surface-filled with elevation (`.card`, `.elev-sm/md/lg`) — borders are not how this system draws a card. The three flagship screens already did this (`rounded-md bg-surface-raised shadow-sm/md`); every other screen touched in this pass (`movimientos`, `privilegios`, `mis-tickets`, `decimas`, `clases`, `clases/[id]`, `test-perfil`'s question cards) had its `rounded-lg border border-surface-border bg-surface-raised` cards converted to match. Two intentional exceptions were left alone: `mis-tickets`' ticket cards, where the border color is semantic (amber/emerald = funding/emitted state, not decoration), and the dashed-border "próximamente" placeholder idiom (`clases/[id]`, `decimas`) documented in the first pass — still deliberately distinct from the pill-badge placeholder idiom.
- **Containers widened, and the freed width used for a second column, not just bigger margins.** "Use more of the screen" was implemented as real 2-up layouts, not wider single-column text: `/movimientos` (`max-w-5xl`, filters sidebar + list), `/decimas` (`max-w-md` → `max-w-5xl`, balance+form sidebar + a `sm:grid-cols-2` history grid — this was the most cramped screen in the app before this pass), `/privilegios` (`max-w-5xl`, `sm:grid-cols-2` privilege cards per category), `/mis-tickets` (`max-w-5xl`, active/history side by side on `lg`), `/clases` (`max-w-5xl`, `sm:grid-cols-2` module cards), `/clases/[id]` (`max-w-4xl`, `sm:grid-cols-2` attachment grid), `/test-perfil` (`max-w-4xl`, `md:grid-cols-2` question cards), `/inicio` (880px → 960px, modest — it only holds two cards plus the new banner now). `/reglas` got a sticky left-hand section nav (`lg:grid-cols-[200px_1fr]`) instead of being widened — legal/policy body text stays at its original ~65ch measure (`max-w-2xl`) for readability; only the layout around it changed.
- **Admin screens (`admin/equipos`, `admin/economia`, `admin/sistema`, `admin/contenido`) got containers widened only** (`max-w-2xl/3xl/4xl` → `max-w-5xl/6xl`), consistent with the "systematic pattern pass, not a bespoke redesign" precedent from the first implementation pass — these are dense, professor-only data/config screens where a full layout rework wasn't reviewed here. The one exception: the two pending-approval queues that are genuinely an action surface (`admin/economia`'s ticket/décimas approval lists, `admin/sistema`'s moderation inbox) went to a responsive 2-column grid (`sm:grid-cols-2` / `lg:grid-cols-2`) so a professor sees more pending work at once — this is a CSS-only reflow of existing cards, not a new layout.
- **Repeated small outline icons moved to `frontend/components/icons.tsx`** (currently `IconRings`, `IconSession`, `IconArrowRight`) instead of being redefined per file — pull from there before adding a new one-off SVG that duplicates an existing glyph.
- **The card elevation pair moved to `frontend/lib/ui.ts`** (`CARD_SM` = `"rounded-md bg-surface-raised shadow-sm"`, `CARD_MD` = the `shadow-md` variant) — a mechanical follow-up to the point above: the same two strings were being hand-typed at every card call site this pass touched, with no shared source of truth. Use `` `${CARD_SM} p-4 ...` `` (append padding/layout classes per call site) instead of retyping `rounded-md bg-surface-raised shadow-sm`. This wasn't extended to every pre-existing card in the app (e.g. `BalanceWidget.tsx`, the admin pages' legacy bordered cards) — only the ones this pass's own diff introduced or edited; migrating the rest is future cleanup, not done here to keep this pass's footprint to the screens it actually touched.

## Third implementation pass: consolidate `/clase1` into `/clases` (2026-08-25)

The professor flagged that `TopNav` showed "Sesiones → Sesión 1" and "Clases" as two separate paths that both read as "the course content" — real, user-visible duplication left over from the first pass's deliberate "leave `/clase1` running in parallel" call. Fixed by merging them into the one real content system instead of just tidying the nav:

- **`CourseSession` gained an `embed_url` column** (`backend/app/models/content.py`, migration `a1c3f6e29b7d`, schemas `CourseSessionDetailOut`/`CourseSessionIn`/`CourseSessionUpdate`) — an optional URL for a session to render as a full iframe (`/clases/[id]/page.tsx`, same treatment `/clase1` used: `w-full rounded-md border`, `height: 80vh`, plus an "Abrir en pestaña nueva ↗" link in the header). This is deliberately separate from `SessionAttachment` (an uploaded, downloadable file) — an embed points at content served some other way (here, a static asset already in `frontend/public/`), not something the backend stores/serves itself. `/admin/contenido`'s session forms (`SessionRow`, `NewSessionForm`) got a matching `EmbedUrlField`, so this isn't a one-off hack for Sesión 1 — any future session can use it the same way.
- **The migration also seeds "Módulo 1 · Introducción" / "Presentación del curso"** pointing `embed_url` at the existing `frontend/public/clase1-content/index.html` (not moved or duplicated — same static asset, same content), unlocked immediately so it's visible without the professor having to unlock it by hand. ## Fourth implementation pass: inline PDF/PPT preview (2026-08-25)

Attachments on `/clases/[id]` previously only offered "Ver / descargar" (fetch-as-blob, open in a new tab or force a download). Requested: a real inline preview for PDF and PPT/PPTX, not just a download.

- **`SessionAttachment` gained a `preview_path` column** (migration `f4a2d8c19e6b`) and a `preview_available` computed property, exposed on `AttachmentOut`. A PDF previews itself; a PPT/PPTX gets converted to PDF via LibreOffice headless (`app/services/content.py`, `_convert_to_pdf_preview` — `soffice --headless --convert-to pdf`, a unique `-env:UserInstallation` profile dir per conversion so concurrent uploads don't contend for the same LibreOffice profile). Word docs and images stay download-only — not asked for, no free way to preview a `.docx` inline in a browser the way PDF/PPT(→PDF) allow. `preview_available` reports `True` for any PDF/PPT/PPTX content-type (`PREVIEWABLE_VIA_CONVERSION_CONTENT_TYPES` in `app/models/content.py`) regardless of whether `preview_path` is already populated — see next point for why.
- **Conversion is attempted at upload time, and lazily on first preview request otherwise** (`services.content.get_preview_source`, called from the `/preview` endpoint). It never raises — on any failure (binary missing, corrupt file, `CONVERSION_TIMEOUT_SECONDS` timeout) it logs and leaves `preview_path` null; the attachment upload itself always succeeds regardless. The lazy fallback exists because upload-time conversion only started existing with this feature — without it, any PPT/PPTX uploaded before this pass (or whose upload-time conversion happened to fail) would show a "Vista previa" button that 404s forever, since nothing ever retries it. `get_preview_source` now converts on demand the first time someone opens the preview and persists the result, so it self-heals instead. There's no background job queue in this project yet, so running the conversion synchronously inside the request (upload or preview, whichever hits it first) is the pragmatic choice, not a placeholder for one — bounded by a 90s subprocess timeout so a pathological file can't hang a web worker indefinitely.
- **`backend/Dockerfile` installs `libreoffice-impress`** — this is the one dependency-weight tradeoff of this feature (adds a few hundred MB to the image); there's no lighter way to render real PPTX content. Verified for real in this pass: converting an actual course deck (`sesion2/*.pptx`) produced a correct 14-page PDF, rendered pixel-correct in a headless-browser screenshot before being wired into the UI.
- **New endpoint `GET /sessions/{id}/attachments/{id}/preview`** (`app/routers/content.py`) — same visibility/auth checks as `/download` (a locked module's attachments don't leak via a preview URL either), serves the PDF (original or converted) with `media_type=application/pdf`.
- **Frontend**: `frontend/lib/api.ts`'s `fetchAttachmentPreviewUrl` mirrors the existing `openAttachment` blob-fetch pattern (`fetch` with a Bearer header → `blob()` → `URL.createObjectURL`) rather than a plain `<iframe src="...">` — the download endpoints require an auth header a bare iframe can't attach, so every file view in this app goes through a client-side blob fetch, preview included. `/clases/[id]/page.tsx`'s attachment list renders each row as an `AttachmentRow` with a "Vista previa"/"Ocultar" toggle (only shown when `preview_available`) that expands an inline `<iframe>` (`70vh`, `sm:col-span-2` so the expanded row takes the full grid width instead of half of it).
- **Preview loads open by default** (revised 2026-08-25, same day): each `AttachmentRow` fetches its own preview blob on mount instead of waiting for a click — a student lands on `/clases/[id]` and every previewable attachment is already showing, "Ocultar" is what's opt-in, not "Vista previa". Once fetched, the blob URL is kept (not discarded) while hidden, so toggling back to "Vista previa" is instant and doesn't re-request or re-convert the file — only a failed load clears it, so clicking "Vista previa" again after an error retries. This trades the original "don't eagerly fetch every PDF" caution for the student not having to hunt for a button per file; each row still loads independently so a session with several attachments shows them as their own fetches resolve rather than blocking on all of them.

### Follow-up pass: staged edits + name/team/tokens (2026-08-26, same day)

The professor flagged two things about the first cut: editing a row (the perfil `<select>`) committed to the API immediately on `onChange` — a stray click could silently reassign someone's profile with no chance to reconsider — and the table couldn't touch name, team, or Tokens balance at all (those still required `admin/equipos`/`admin/economia`, or weren't editable anywhere).

- **All row edits are now staged, not live.** `nombre`/`apellidos` (now plain text inputs), `perfil` (the existing `<select>`), `equipo` (a new `<select>` of existing teams + "Sin equipo"), and `saldo` (a new number input) all write to a page-level `drafts: Record<userId, RowDraft>` state — nothing calls the API on `onChange`. A dirty row gets a subtle `bg-accent-900/10` tint (row-level, not per-cell — simplest legible signal that something on that row is unsaved). A footer bar below the table (**not** the header — "add a button at the bottom" was explicit) shows the pending-change count and two buttons: **Descartar cambios** (resets every draft back to the last-loaded server value) and **Guardar cambios** (fires one API call per changed field, per dirty row, in parallel). Approve/Reject/Reset PIN/Desactivar stay immediate, single-click actions with their own confirm dialogs, exactly as before — those are deliberate one-shot actions, not the accidental-edit risk the professor was flagging, so they weren't folded into the staging model.
- **Partial-failure handling**: after "Guardar cambios", rows that saved cleanly reset their draft to the fresh server value (via a full `reload()`); rows where any field's call failed keep their in-progress draft untouched (the reload passes a `preserveIds` set) and show the error inline, so a bad edit on one row never wipes out what the admin typed there — they can fix it and hit Save again without redoing the rest of the batch.
- **Backend additions**: `POST /admin/users/{id}/rename` (`RenameUserIn`, same length limits as registration) and `POST /admin/users/{id}/team` (`SetTeamIn`, `team_id: int | None`) in `admin_users.py`. The team move itself lives in a new service function, `services/teams.py::set_user_team` — same altitude call as the batched team/balance lookups added with the first cut of this screen: membership mutation is Dominio 2 (Teams) business logic, so it belongs in `services/teams.py` even though the endpoint is reached via the user-centric `/admin/users/{id}/...` path (mirroring `reassign-profile`'s sibling routes). It closes the user's current active `TeamMember` row (`left_at`, never deleted — same "soft leave" convention `get_active_team_of_user` already relies on) and opens a new one, or just closes it if the new `team_id` is `null`.
- **Token edits reuse the existing `POST /admin/tokens/adjust`** (`admin/economia`'s manual-adjustment endpoint) rather than adding a new one — the table computes `delta = draft.balance - baseline.balance` client-side and sends that. Its `nota` field is mandatory server-side, so a single shared "Nota del ajuste de tokens" input appears in the footer bar (only when at least one row's balance was actually edited) and gates the Save button — one justification note per save batch, not one per row, since asking for a separate note per edited balance would make batch-correcting several students' Tokens tedious for no real audit benefit.
- **No new backend endpoint for Tokens**, and no new one for `perfil` either (still `POST /admin/users/{id}/reassign-profile`) — only name and team needed new endpoints; reuse was checked first per the project's own workflow rule before adding anything.

- **New component pattern: animated tank/gauge (`TankVisual`).** A 160×220 inline SVG — an outlined rounded-rect "tank" body, a `<clipPath>`-masked fill `<rect>` whose height animates from 100% down to the final concentration (as a % of the case's initial concentration), and a dashed horizontal line marking the case's max-acceptable threshold. This is a genuinely new visual primitive (no existing progress-bar/gauge component covers it) — reuse it (or its clip-path-masked-fill technique) for the next case that needs a "level draining/filling toward a threshold" visualization, rather than inventing a second one. The fill color is neutral (`accent2-500`, `#9690c9`) while animating and only resolves to the outcome color (emerald/amber/red, see below) once the animation completes — this reads as "we don't know yet" during the simulation and "here's what happened" at the reveal, rather than spoiling the outcome from frame one.

- **Consequence reveal reuses the `ProfileResultScreen` shell** (icon-in-tinted-circle + `animate-popIn` + kicker/title/description, `animate-fadeUp` card entrance) documented above, extended with an optional stats grid (`ConsequenceStat`) for the tangible-consequence numbers — money lost, patients affected, repair cost — using `BalanceWidget`'s `useCountUp` (now exported, not copied, so this is the second consumer of one shared hook rather than a duplicate). This is the first screen to apply that result-shell idiom to something other than a one-time onboarding result, and the first to use `useCountUp` outside the token balance card — confirms the pattern generalizes; reuse both for the next "reveal an outcome" screen instead of hand-rolling either.
- **Consequence color mapping reuses the existing status-color convention** (`mis-tickets`/`decimas`'s `StatusBadge`: emerald = success, red = failure, amber = a lesser-severity warning) rather than inventing a fourth palette: correct → emerald, "lote perdido" (missed the deadline) → red, "línea dañada" (met the deadline but exceeded the pressure limit — a real but less catastrophic failure mode) → amber. No new token was needed.
- **Scope note**: this PR ships the full student-facing flow and the backend podium/Tokens integration (`cerrar_licitacion` computes arrival order among correct responses and credits Tokens via the shared ledger). It does not implement §10's real-time WebSocket podium engine or the "planteo" (draft) phase — each team submits one final REST answer, and the podium is computed by submission order at close time. This is a documented, deliberate cut (see `backend/app/models/licitaciones.py`'s module docstring), not an oversight — building it is real future work, not a follow-up nit.
